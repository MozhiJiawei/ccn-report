Mental model first

01 / ProblemWhy this exists

Background

传统 GPU 推理系统里，主机 CPU 常在“调度完成后”变成未充分利用资源

如果所有请求都排队等最大 GPU 模型，轻量任务也会消耗昂贵 GPU 服务窗口；同时 GPU 服务器里的 CPU 只做调度、tokenization、数据搬运，剩余核心没有直接创造并发。

单一路径心智模型

User request所有任务先进入同一个生成服务
→
GPU 405B重生成、轻摘要、校验都可能排队
→
Response吞吐受单一路径容量约束

材料中的问题定义

现象影响
GPU 承担大多数推理轻任务也占用大模型服务能力
CPU 在调度后空闲同一台服务器的已购算力没有转成用户并发
端到端流水线串行Research + Write + Review 延迟累加

[1] Intel blog: LLM serving systems often allocate most inference to GPUs while CPU resources are underutilized. [2] Whitepaper executive summary: CPUs in GPU systems often remain idle after scheduling, tokenization, and data movement.

Read this slide as: resource waste, not model-quality problem

05 / Compute scaleAMX matrix vs AVX-512 vector

Theoretical peak, not vLLM throughput

双路 Xeon 6776P 的 AMX BF16/FP16 理论峰值约 302-472 TFLOPS；AVX-512 向量估计约 18.8-29.5 TFLOPS

这一页只解释“矩阵引擎比向量引擎大一个数量级”的硬件心智模型；base 到 all-core turbo 是理论峰值区间，不是 vLLM 实测吞吐。

项目公开/派生口径结果边界
AMX BF16/FP161024 ops/cycle/core x 128 cores x 2.3-3.6GHz约 302-472 TFLOPS理论峰值区间
AMX INT82048 ops/cycle/core x 128 cores x 2.3-3.6GHz约 603-944 TOPS理论峰值区间
AVX-512 BF16/FP16Intel 称 AMX BF16/FP16 MAC up to 16x AVX-512，故 AMX/16约 18.8-29.5 TFLOPS派生估计
不要把 302-472 TFLOPS / 603-944 TOPS 写成“CPU 8B endpoint 实测吞吐”。它们是基于官方 ops/cycle/core、核心数、base clock 和 all-core turbo 上界的理论峰值。

07 / GPU scale comparisonXeon AMX is not GB200 tensor compute

Positioning boundary

与 GB200 Superchip 相比，双 Xeon AMX BF16 理论峰值约低 10.6-16.6x（dense），或 21.2-33.1x（sparse）

因此本方案的正确定位不是“CPU 替代 GB200/B200 GPU”，而是让闲置 host CPU 承接小模型、校验、路由和短任务。

10 / Latency evidence gapDo not invent CPU 8B latency

Critical correction

公开材料没有披露 CPU 8B endpoint 的最终 TTFT/TPOT 实测值

“新增 56 个 CPU users”必须理解为 benchmark 在 SLA 口径下搜索出的并发结果；不能写成 CPU 8B 延迟已经被证明是多少 ms。

证据项公开材料实际披露不能推出
benchmark_results.md/json白皮书说流程会生成并用于比较 concurrency、TTFT、TPOT没有给出 CPU 8B p99/mean 数值
并发结果GPU-only 127；CPU-GPU co-serving 新增 56 CPU users，总计 183不能等同于 CPU 8B 延迟 X ms
Demo SLA defaultsSLA_TTFT_MS=10000；SLA_TPOT_MS=100这是阈值/默认值，不是实测结果

给小白的读法

TTFTTime To First Token：从请求发出到第一个 token 出来的时间，影响“有没有卡住”的体感。
TPOTTime Per Output Token：生成每个后续 token 的平均耗时，影响输出流畅度。
正确写法：公开材料支持“CPU endpoint 在 benchmark SLA 搜索口径下增加 56 users”。错误写法：CPU 8B endpoint 已证明 TTFT=10000ms、TPOT=100ms，或实测延迟是多少。

[2] Whitepaper: benchmark flow generates benchmark_results.md/json for concurrency, TTFT, and TPOT criteria; visible text reports concurrency outcome only. [8] Intel AI TCE cpu_binding_demo script defaults: SLA_TTFT_MS=10000 and SLA_TPOT_MS=100, with extraction logic but no committed final measurements.

13 / Power boundaryPackage, system, rack are different mouths

Power and efficiency framing

功耗不能把 700W CPU TDP 与 120kW GB200 rack power 当成同一边界硬比

异构推理的收益来自复用 GPU 服务器内已供电、已部署的 host CPU 余量，而不是 CPU 替代 GPU 的能效曲线。

对象公开功耗口径边界读法
2 x Xeon 6776P350W TDP/socket；双路 700W CPU TDPCPU package-level只覆盖 CPU 封装热设计，不含整机
NVIDIA DGX B200约 14.3kW max8 x B200 system-level包含 GPU 系统组件，非单 GPU TDP
DGX GB200 / NVL72约 120kW rack powerrack-level包含 Grace、Blackwell、NVLink/NVSwitch、电力与冷却设计

14 / Operational mechanismBinding and pipeline

Operational detail

要让 CPU 帮忙而不拖累 GPU，关键是 CPU binding 与流水线重叠

CPU binding 的判断

56CPU users with proper binding
51CPU users without binding across all CPUs
含义：GPU 服务需要 NUMA-local CPU 和可能的 PCT 核心保护；剩余 CPU 再给 CPU-only inference。
边界：binding 是部署策略，不是模型算法本身。配置不当会吞掉一部分 CPU 端收益。

流水线延迟心智模型

Sequential latency = Research + Write + Review
Pipelined latency ~= MAX(Research, Write, Review)
ResearchCPU 先产出 notes
↘
WriteGPU 拿 partial context 先写
↘
ReviewCPU 拿 partial draft 反馈

[2] Whitepaper: CPU binding generated Docker Compose override; GPU services run on NUMA-local CPUs; CPU-side supported users dropped from 56 to 51 without binding. [1] Intel blog latency formulas.
