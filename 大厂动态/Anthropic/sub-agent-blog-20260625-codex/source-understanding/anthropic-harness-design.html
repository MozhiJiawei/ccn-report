Harness 的价值不在“多 agent”，而在把模型短板显性化后再编排

Anthropic 这篇文章给出的核心判断是：长任务失败来自上下文、规划、自评和真实交互验证的组合缺口；harness 设计要随模型能力迁移而持续删改。

Published: 2026-03-24
页面判断
长运行应用开发需要的是“可检验的工作系统”，不是更长提示词。
文章把 frontend design 与 full-stack coding 放在同一框架下：先定义可评分标准，再用独立 evaluator 形成反馈循环，最后用 planner / generator / evaluator 把任务变成可协商、可验收、可迭代的工作流。
问题根因长上下文导致 coherence 下降，模型还会在接近上下文上限时提前收尾；自评又倾向于过度乐观。
机制抓手把“写代码”和“判断质量”拆开，让 evaluator 用 Playwright 实际操作应用，并用阈值决定 sprint 是否通过。
关键边界harness 带来明显质量提升，但成本和耗时很高；随着模型升级，原本 load-bearing 的结构可能变成开销。

Source Understanding / 02

朴素长任务 agent 会同时遭遇上下文衰退和自评失真

文章先定位两个失败模式：长任务中 coherence 下滑或提前收尾，以及模型评价自己产物时倾向于“自信地夸好”。
章节：Why naive implementations fall short
用途：解释为什么需要 harness，而不是直接让一个 agent 跑到底。
上下文
长任务越跑越散。上下文窗口填满后，模型更容易失去连贯性；有些模型出现“context anxiety”，会在它以为接近限制时过早结束工作。
重置
reset 与 handoff 解决一部分问题。清空上下文再交给新 agent，可去掉焦虑和历史噪声，但要求 handoff artifact 足够完整。
自评
同一个 agent 很难严厉审自己。尤其在设计这类主观任务里，没有二元测试，模型会把普通作品评得过高。
外评
独立 evaluator 更可调。把 evaluator 调成更怀疑、更具体，比让 generator 自我批判更容易；反馈也能变成下一轮迭代输入。

Source Understanding / 03

Frontend 实验把“审美”转成可迭代的评分循环

Anthropic 先在 frontend design 上验证 generator-evaluator 模式：rubric 让主观品味可操作，Playwright 让 evaluator 看到真实页面。
章节：Frontend design: making subjective quality gradable
角色：为 full-stack harness 提供原型。

四项评分维度

Design quality颜色、排版、布局和图像是否形成整体情绪与身份。
Originality是否有定制决策，而非模板、默认组件和常见 AI 样式。
Craft层级、间距、对比度、色彩和技术基础是否可靠。
Functionality用户能否理解、找到主要动作并完成任务。
Prompt用户给出站点或应用诉求
Generator生成 HTML / CSS / JS 前端
Evaluator用 Playwright 浏览、截图、评分与写 critique
5-15 次迭代：分数上升后平台期；可继续 refine，也可 pivot 到新美学方向

关键理解

这不是把审美完全量化，而是把“什么算好”拆成足够具体的检查项。rubric 本身会影响 generator 的美学方向，所以 evaluator 不是中立仪表，而是 harness 设计的一部分。

Source Understanding / 04

三 agent 架构把高层目标压成可验收的 sprint contract

full-stack harness 的关键不是角色数量，而是让 spec、实现和 QA 在每个工作单元前先对齐“done”的含义。
章节：Scaling to full-stack coding / The architecture
对象：planner, generator, evaluator。
Planner从 1-4 句 prompt 扩展为产品 spec；关注产品语境和高层技术设计
Generator按 feature / sprint 实现 React, Vite, FastAPI, SQLite/PostgreSQL 应用
Evaluator用 Playwright 实测 UI、API、数据库状态，并按阈值判定通过
Sprint contract：generator 提案“做什么 / 如何验证”，evaluator 审核并协商到一致后再写代码

文件通信

文章描述 agents 通过文件读写通信：一个 agent 写文件，另一个读后在同文件或新文件中回应。这样避免一开始过度指定实现细节，同时让实现忠于 spec。

为什么 contract 是 load-bearing

桥接抽象差距planner 的 spec 故意保持高层，contract 把用户故事转成可测试行为。
防止错误级联不让 planner 预先写死细节，减少错误技术选择一路传导。
硬阈值失败任何评分维度低于阈值，sprint 就失败，generator 获得具体反馈。
证据定位：网页 lines 62-70 描述三 agent persona、criterion threshold、contract negotiation 和文件通信。

Retro 游戏案例证明 harness 用 20x+ 成本换来核心功能可用

第一版 full harness 与 solo 对比：solo 更便宜更快，但关键 gameplay 断裂；full harness 更贵更慢，却交付了更完整、更可玩的应用。
案例：2D retro game maker
模型：Claude Opus 4.5。

Full harness 时长，成本约 $200。
20x+

维度SoloFull harness
范围看似符合预期，但功能浅。planner 扩展为 16 个 feature / 10 个 sprints。
核心玩法实体出现但不响应输入，game runtime wiring 断裂。用户能移动 entity 并实际游玩，虽然物理和关卡仍有瑕疵。
QA 证据问题靠作者手动点击后发现。evaluator 按 sprint contract 逐条测试，发现具体代码和 API 问题。

Evaluator 捕获的具体缺陷

矩形填充工具函数存在但 mouseUp 没有正确触发，只在拖拽起止点放置 tile。

Source Understanding / 06

模型升级后，sprint 不再固定必要；evaluator 价值取决于任务是否越界

文章最重要的工程启发是：每个 harness 组件都代表一个“模型做不到”的假设，模型变强后必须重新压力测试这些假设。
章节：Iterating on the harness / Removing the sprint construct
模型变化：Opus 4.5 到 Opus 4.6。

结构删减逻辑

组件第一版作用更新后判断
Context reset解决 Sonnet 4.5 的 context anxiety。Opus 4.5 已基本不需要，改为连续 session + automatic compaction。
Sprint construct把工作拆小，帮助模型保持 coherence。Opus 4.6 能连续 build 两小时以上，sprint 可被移除。
Planner避免 raw prompt 导致 under-scope。仍保留；没有 planner，generator 会先开工并做得不够丰富。
Evaluator逐 sprint 捕获 bug 并维持 spec 对齐。改为末尾 pass；在模型可靠范围内是开销，在能力边缘仍有 lift。
方法论判断
Harness 不是模板，而是一组会过期的能力补丁。
正确维护方式是读取真实 trace，逐个移除组件并观察质量变化；如果某个组件不再承载性能，就应删掉或降频。
证据定位：网页 lines 126-138 说明逐个移除组件、Opus 4.6 能力提升、sprint 移除和 evaluator 的条件价值。

Source Understanding / 08

对应用开发团队的可复用结论：先定位短板，再选择最小 harness

这篇文章不是给出固定三 agent 模板，而是给出一个调参循环：真实任务 trace、明确验收标准、独立检查、组件压力测试。
章节：What comes next
输出：可转为 PPT Content Brief 的主结论。
1
先证伪朴素方案
在真实长任务上看 trace，确认失败来自上下文、规划、自评、交互验证还是产品直觉。
2
把质量写成可判定标准
设计任务也要有 rubric；软件任务要把“完成”变成可点击、可请求、可查库的验收项。
3
分离执行与判断
generator 负责产物，evaluator 负责怀疑；如果 evaluator 太宽松，读日志并调它的判断。
4
让结构随模型迁移
每个组件都是能力补丁；模型变强后要逐项删减，避免旧假设变成成本和延迟。

可见总结

Anthropic 的 harness 经验说明：长运行 agentic coding 的工程重点，是把目标拆成可协商的契约，把质量判断外置成可调 evaluator，并在模型升级后反复检查哪些脚手架仍然真正承载性能。

证据定位：网页 lines 177-180 给出最终观点：持续实验、读取 traces、按复杂度使用分解与专门 agent，并在新模型到来时重新审视 harness。
