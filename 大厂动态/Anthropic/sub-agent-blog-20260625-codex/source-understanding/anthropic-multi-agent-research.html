Source Understanding

Anthropic 的多智能体研究系统，用并行 token 预算换取开放式研究质量

对象：Anthropic Engineering 文章《How we built our multi-agent research system》，2025-06-13。本文只基于该网页，不扩展额外来源。

01 / 08

核心判断：多智能体不是“更多角色扮演”，而是把搜索、压缩、工具调用和上下文窗口分摊到多个并行执行单元。

  • 价值来自并行广度适合需要同时追多条线索、资料超过单一上下文、且任务价值足以覆盖成本的研究问题。
  • 架构核心是编排LeadResearcher 负责策略、分解和综合，Subagent 独立搜索并压缩发现，CitationAgent 做归因。
  • 上线难点在行为可靠性prompt、工具描述、eval、追踪、checkpoint 和部署节奏共同决定系统是否可生产化。

Fit

多智能体适合“广度优先”研究，不适合强共享上下文任务

文章把适用性定义在任务结构上：线索可拆、方向可并行、信息量大、工具多；反面是依赖密集、实时协调要求高。

02 / 08

适配条件

条件系统收益
开放式问题步骤难提前固定，agent 可以根据中间发现调整路线。
并行方向不同 subagent 同时探索独立线索，减少单一路径依赖。
海量资料每个 subagent 拥有独立上下文，先局部压缩再交给 lead 综合。
复杂工具不同工具和来源可以分配给不同任务边界，降低混用成本。

不适配边界

  • 上下文必须共享如果所有 agent 都必须实时掌握同一完整状态，独立上下文会变成协作负担。
  • 任务依赖密集编码任务常常并行面较少，实时委派和协调能力不足会抵消收益。
  • 价值低于成本文章强调系统 token 消耗高，只有高价值任务才具备经济性。
PPT 可用判断：它是一种“高成本换广度”的架构选择，不是所有 agent 产品的默认答案。
Evidence: article sections “Benefits of a multi-agent system” and examples of breadth-first research vs coding tasks.
Architecture

系统把研究拆成计划、并行搜索、综合和引用四段

LeadResearcher 是控制面，Subagent 是并行工作面，CitationAgent 是归因面；Memory 用来抵御长上下文截断。

03 / 08
1. User query 用户提出研究问题

问题通常开放且难以预先固定路径。

2. Lead 制定策略并保存计划

LeadResearcher 先思考路线，并把计划写入 Memory。

3. Subagents 并行搜索不同切面

每个 subagent 带着明确任务、工具边界和输出格式独立调查。

4. Synthesis 综合后决定是否加搜

Lead 汇总发现，判断是否继续生成 subagent 或收敛答案。

5. Citations 引用 agent 定位出处

CitationAgent 把报告 claim 对齐到具体文档位置。

相对 RAG 的差异传统 RAG 偏静态相似度检索；该系统强调多步动态搜索、基于发现改写路线。
上下文策略计划和阶段性信息外置到 Memory，避免超过 200k token 后丢失关键研究意图。
压缩机制Subagent 先把局部语料压成高价值发现，lead 只消费压缩后的结果。
归因机制最终答案前新增 CitationAgent，说明生产系统把“生成答案”和“核对出处”拆开。
Evidence: article “Architecture overview for Research” and workflow diagram description.
Performance

性能提升主要靠“花够 token”，但成本也同步放大

Anthropic 的解释不是单个 agent 更聪明，而是多上下文并行让系统能投入更多搜索、推理和工具调用。

机制解释

机制为什么影响结果代价
独立上下文每个 subagent 可追一条线索，不必挤在同一窗口里。综合和去重成本上升。
并行工具lead 可同时生成 3-5 个 subagent；subagent 也可并行调用多个工具。错误路径也会被快速放大。
模型升级文章称 Claude Sonnet 4 对 token 使用效率的提升超过简单翻倍预算。结论依赖 Anthropic 内部模型和评测。
经济门槛15x chat token 消耗要求任务价值足够高。低价值查询会过度投资。
页面判断可写成：多智能体的第一性收益是“并行投入更多有效搜索预算”，不是神秘的涌现协作。
Evidence: internal research eval, BrowseComp variance analysis, token consumption and parallelization claims in the article.
Prompt + Tooling

Prompt 工程的重点，是给编排器清晰的委派协议

早期失败包括过度生成 subagent、无效搜索和互相干扰；Anthropic 通过任务边界、努力预算、工具启发式和可观察模拟来修正。

05 / 08

委派要完整

  • 目标每个 subagent 必须知道自己回答哪个子问题。
  • 边界说明该查哪些来源、用哪些工具、不要查什么。
  • 格式返回结构需要能被 lead 直接综合。

努力要分档

查询类型推荐投入
简单事实1 个 agent，约 3-10 次工具调用。
直接比较2-4 个 subagent，每个约 10-15 次调用。
复杂研究10+ subagent，并且职责拆分清楚。

工具要可选对

  • 先看工具让 agent 先理解可用工具，再决定路线。
  • 专用优先能用专业工具时，不默认泛化搜索。
  • 描述可测Anthropic 用 tool-testing agent 改写工具描述，使后续完成时间下降 40%。
Evidence: article “Prompt engineering and evaluations for research agents,” including delegation, scaling rules, tool descriptions and self-improvement loop.
Evaluation

评估不能检查固定路径，只能检查结果质量与合理过程

多智能体同题可能走出不同有效路线，因此 eval 需要从路径一致性转向结果、引用、完整性、来源质量和工具效率。

06 / 08

评估框架

维度判定问题来源证据
事实准确回答里的 claim 是否匹配来源。LLM judge rubric。
引用准确引用来源是否支撑对应 claim。CitationAgent 与 judge 标准。
覆盖完整用户要求的各方面是否都被回答。research output rubric。
来源质量是否优先权威/一手来源。人工测试发现 SEO 内容偏差后增加启发式。
工具效率是否用了合适工具和合理调用次数。rubric 中的 process 判断。

操作经验

  • 小样本先跑早期改动效应大，约 20 个真实查询就能发现显著差异。
  • 单 judge 更稳文章称一个 LLM 调用输出 0-1 分数和 pass/fail，比多 judge 组合更一致。
  • 人工补盲区人类测试能发现自动 eval 忽略的幻觉、系统失败和来源选择偏差。
适合放进 PPT 的判断：agent eval 的对象不是“有没有按剧本走”，而是“是否到达可验证的好结果”。
Evidence: article “Effective evaluation of agents” and appendix note on end-state evaluation.
Reliability

生产化难点来自状态长、错误会复合、部署不能打断运行中 agent

文章把“last mile”描述为主要工程工作：durable execution、错误恢复、全链路追踪、隐私友好观测和 rainbow deployments。

07 / 08

可靠性问题链

State长时间运行保留状态

多个工具调用之间的局部失败会影响后续路线。

Failure小错误会放大

一次工具失败或错误来源可能把 agent 带到完全不同轨迹。

Recovery不能简单从头重启

重启成本高且影响用户体验，需要 checkpoint 和 resume。

工程应对

做法作用
告知工具失败利用模型适应性，让 agent 改换路线或降级处理。
重试与 checkpoint用确定性保护兜住可预期故障。
生产 tracing定位“为什么没找到明显信息”：查询差、来源差还是工具故障。
高层行为观测不读取对话内容，也能看决策模式和交互结构。
Rainbow deployments新旧版本同时运行，避免更新破坏正在执行的 agent。
架构未完全解决同步瓶颈：lead 仍等待一批 subagent 完成，异步化会增加状态一致性和错误传播难度。
Evidence: article “Production reliability and engineering challenges.”
