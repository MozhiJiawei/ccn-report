这不是“所有 AI 响应都快 92%”的通用结论。原始证据指向 Llama 3.1 8B Instruct、shared prefix workload、8×A100 40GB、GKE Inference Gateway 对比 round-robin HTTP 负载均衡。

Evidence Scope

92.8% 是 TTFT 口径，不是端到端全量用户体验口径

Google 的博客把“AI responses”写得很大，但表格里的最大数字只对应 mean time to first token。更完整的表达应该同时带上 workload、对照组和硬件条件。

Google Cloud Blog Figure 3
精确表格口径

Throughput: 7,169.21 vs 6,042.05 output tokens/s (+15.7%)
TTFT: 188.36 ms vs 2,624.73 ms (-92.8%)
ITL: 30.20 ms vs 81.03 ms (-62.6%)

已知 benchmark 条件

Llama 3.1 8B Instruct；shared prefix workload；8 块 NVIDIA A100 40GB；对照组是第三方托管 Kubernetes + conventional round-robin HTTP load balancing。

Mechanism

关键不是缓存本身，而是每个请求都被送去“已有前缀”的副本

vLLM 等模型服务端可以做 prefix caching；GKE Inference Gateway 的价值是把 Kubernetes 网关层变成推理感知调度器，让缓存更可能命中。

GKE request flow
EPP 是路由大脑Gateway 调用 Endpoint Picker，再把请求转给选中的 model server。

Prefix cache aware

跟踪每个 model server 的 prefix cache indexes，长匹配得分更高。

Load aware

读取 KV cache utilization 和 pending queue depth，避开拥堵副本。

LoRA aware

优先已有目标 LoRA adapter 或仍有装载空间的副本。

结论边界

缓存感知路由把 prefill 重算变少；它不替代模型 server 内部优化。

Sources: Google Cloud Docs llm-d Router and traffic distribution sections; Google Cloud llm-d blog.

Product Anatomy

GKE 把 llm-d Router 包进 Gateway API 的产品面

它不是一个单独的模型 server，而是把 Kubernetes Gateway、InferencePool、InferenceObjective、EPP 和模型 Pod 串成托管推理入口。

GKE resource model
不是单点网关Gateway + InferencePool + Objective + 安全/观测/模型 server 共同构成产品面。
产品层价值：用 Kubernetes 原语治理 LLM serving

InferencePool

一组共享模型、加速器和 server 配置的 Pods。

InferenceObjective

声明模型名、Priority、LoRA 等 serving 属性。

GKE Gateway + EPP

数据面和路由智能分离，EPP 独立扩缩。

Source: google-docs-about-gke-inference-gateway/source.md, key concepts and llm-d Router sections.

llm-d Route

llm-d 的路线是 Kubernetes-native 分布式推理，而不仅是一个网关插件

Google 的 llm-d 博客把它描述为 vLLM 之上的分布式 serving stack：调度器、prefill/decode 分离、多层 KV cache 共同服务于低延迟和低硬件消耗。

llm-d stack architecture
三条主线

vLLM-aware scheduler；Prefill/Decode 分离；Multi-tier KV cache。

边界

Google 另称代码补全 TTFT 早测提升 2x，但未给模型、流量和方法细节。

Source: google-llm-d-vllm-distributed-inference/source.md.

Competitor Frame · NVIDIA Dynamo

Dynamo 把竞争点推到 GPU fleet 级：KV-aware router + NIXL + KVBM

与 llm-d 一样，Dynamo 也不把推理优化停在 HTTP 负载均衡；它把路由、P/D 分离、KV 迁移和 Kubernetes 调度拆成一套数据中心级推理编排框架。

NVIDIA Dynamo architecture and components
与 llm-d 的同层比较

Dynamo 也有 KV-aware Router 和 disaggregated serving；差异是它更强调 NIXL 低延迟数据传输、KVBM 层级 KV 管理、Grove 拓扑感知 Kubernetes 调度。

Source: nvidia-dynamo-inference-framework/source.md.

Competitor Frame · AIBrix

AIBrix 更像 vLLM 生产控制面：Gateway、routing、autoscaling、distributed KV cache

AIBrix 没有在文章里直接点名 llm-d，但它覆盖的控制面问题高度相似：多模型/多副本路由、LoRA 管理、跨 engine KV 复用、多节点编排和 SLO 约束。

AIBrix control-plane diagram
Gateway

LLM Gateway and Routing

管理多模型、多副本请求入口，按资源、负载和异构性做感知路由。

KV Cache

Distributed KV Cache

支持高容量、跨 engine KV 复用；路线还包括 P&D aggregation、request migration、cross-instance reuse。

Control

QoS / Priority / Fairness

把传统资源治理原则引入请求级多租户，目标是 SLO-guaranteed inference。

Boundary

本页非 benchmark

文章说明 ByteDance 生产使用和能力范围，但没有给与 llm-d/GKE 可直接对比的性能数字。

Applicability

要复现 92% 级 TTFT，业务流量必须“长前缀重复”

这类方案最怕两个误配：一是业务流量几乎没有共享 prefix；二是平台没有把 cache hit、队列、LoRA、priority 这些信号接到路由层。
