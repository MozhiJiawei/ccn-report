Codex 长任务的关键变化不是“更聪明”，而是能在可验证循环里保持更久

这篇文章用一次设计工具实验说明：长时程 agent 工作的可靠性来自模型能力、工具反馈、外部化项目记忆和持续验证共同形成的操作系统。

Mechanism
Article section: “Why Codex can stay coherent on long tasks.”

Codex 不是靠一个巨大 prompt 坚持 25 小时，而是靠循环把错误变成下一步输入

文章把长时程能力解释为 harness 与模型共同运转：仓库、文件、差异、日志和命令输出构成可观察状态。

Plan把开放任务拆成可执行序列
→
Edit在限定范围内修改代码
→
Validate运行 tests / build / lint / typecheck
→
Repair根据失败日志修复，再回到循环
反馈来源：错误、diff、日志、测试结果让 agent 不必凭内部记忆猜状态。
可控性来源：人类可以在中途转向，文章强调 course correction 不需要清空进度。
页面判断：长任务可靠性来自闭环，不来自一次性生成 3 / 7
Durable Project Memory
Article section: “The key idea: durable project memory.”

四类 Markdown 文件把“意图、计划、执行规则、审计记录”分别固定住

这是文章最可复用的操作模式：不是让 agent 记住一切，而是让它反复回读稳定项目状态。

Prompt.md
冻结目标：目标、非目标、硬约束、交付物和 done-when 检查。
防漂移：避免 agent 做出“看起来厉害但不符合规格”的东西。
Plan.md
切分里程碑：每步足够小，能在一个循环中完成并验证。
防震荡：验收标准、验证命令和决策记录减少反复改方向。
Implement.md
运行手册：跟随计划、保持 diff 聚焦、每个里程碑后验证。
防失控：失败先修复，不能带着红灯进入下一阶段。
Documentation.md
共享记忆：当前状态、已完成项、下一步、运行方式和已知问题。
可审计：人类离开数小时后仍能理解发生了什么。
页面判断：外部化记忆比长上下文更像项目管理原语 4 / 7
Verification Gates
Article section: “Verification at every milestone.”

长时程任务的质量门槛不是“能编译”，而是每个里程碑都能被验证和修复

作者强调 Codex 在每个完成点运行 lint、typecheck、tests、build 等命令，并在失败后修复再继续。

质量动作 验证对象 对长任务的作用 失败处理
Lint / format 代码风格、静态规则 避免小错误在 25 小时运行中堆成维护成本 按日志定位并改到规则通过
Typecheck 类型契约、模块边界 让大规模增量代码保持可组合 修复签名、状态和组件接口不一致
Tests 功能行为、边界条件 把“看起来完成”转换成可回归证据 先修失败用例，再进入下一里程碑
Build / export 端到端集成、可交付性 确认产物可以真实运行或导出 修复构建链和运行时破损
页面判断：验证命令是长时程 agent 的导航仪 5 / 7
Evidence Boundary
Article sections: setup, built capabilities, takeaways.

这篇文章证明的是“可委派工作切片变大”，不是证明任意软件都能无人生产上线

证据强在单次高强度工程实验和清晰过程记录；边界在于它不是多任务统计评估，也不是产品级交付验收。

强证据
任务复杂设计工具同时覆盖 UI、数据模型、编辑操作和大量边界条件，作者称其很难“糊弄过去”。
过程可查会话统计、截图、文件栈和验证命令共同支撑“不是一次性生成”的判断。
产物可测实现功能覆盖画布、协作、检查器、图层、原型、评论、导出等高层能力。
限制边界
单次案例文章未给出多任务成功率、消融实验或与其他 agent 的统一对照。
非生产口径作者明确说结果不完美，也不是 production-ready。
强约束环境成功依赖明确规格、稳定文件记忆、验证门禁和 Codex harness；不能外推到无护栏场景。
结论口径：可把它当作长时程 Codex 工作流的来源理解和方法样本，不应把它当作通用 autonomous coding 成功率声明。
页面判断：证据可支持方法论，不支持无限泛化 6 / 7
Reusable Operating Model
Takeaways derived from the provided article only.

复用这篇文章的做法时，应把 Codex 当成“带护栏的长期 teammate”来配置

人类的关键工作从逐行监督转为：定义目标、设置里程碑、规定验证、保留状态、在检查点转向。

任务入口

写清规格：目标、非目标、硬约束、交付物、done-when。没有稳定规格，长时程只会放大漂移。

执行节奏

切成里程碑：每个阶段都要有验收标准和验证命令，失败先修复。

状态管理

持续写文档：用状态和决策记录让人类随时接管或调整方向。

适合委派 需要人工把关 暂不宜放手
实现明确功能、补测试、修验证失败、生成文档状态 架构方向、产品取舍、设计体验、里程碑验收 无规格探索、不可回滚生产操作、缺少验证命令的关键变更
一句话基线：长时程 Codex 的可靠性来自“明确意图 + 外部记忆 + 验证闭环 + 人类检查点”，而不是把一个超长 prompt 丢给模型。
