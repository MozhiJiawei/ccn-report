真实执行链路 · 从指派任务到归档报告

这次不是“多个 agent 一起工作”，而是一条被用户持续校准的生产链

核心链路：用户指派任务 → 主 agent 寻源和加载 skill → 子 agent 解析 PDF → 主 agent 基于 XML 做 source understanding → checker 子 agent 做 QA loop → HITL 对齐 PPT 大纲 → 子 agent 做 HTML → 主 agent 审阅修复 → 子 agent 转可编辑 PPTX → 主 agent 归档。

Page 1 · 真实执行链路总览

01 · 用户输入不是一次性 prompt

用户在关键节点持续改变链路方向

这次 workflow 的每次转向，都来自用户新的约束：论文解析、读者校准、brief 标题、页数、HTML/PPTX 交付、归档和复盘粒度。

起点
“使用 ppt-deep-search 做 SlidingServe 技术热点的 PPT 深度研究”

这决定了主 agent 先加载 ppt-deep-search，而不是直接写 PPT。

论文输入
“这是论文，下载到 .tmp，并让子 agent 用 grobid_pdf_skill 解析”

这把工作链路从网页来源切换为 paper/XML pipeline。

读者校准
“看不懂，技术名词太多”

这触发 Source Understanding 重写：从论文评审语气改成技术小白可理解。

Brief HITL
“标题用这个；分析总结两个，一个讲方法，一个讲效果；1页”

这把最终内容压成单页 Summary，而不是多页技术报告。

交付形态
“子 agent 制作 HTML；再用原生 PPT skill 转可编辑；最后归档”

这形成 HTML → PPTX → ccn-report 的交付链。

复盘要求
“主Agent子Agent要画到一个图里；每个点分别做一页”

这决定本 deck 的复盘粒度：先拆点，再考虑串起来。

Page 2 · 用户输入与链路转向

02 · 主 agent 的寻源与 skill 加载

主 agent 先搭工作台：找来源、读规则、确定阶段 gate

在任何子 agent 启动前，主 agent 先把任务边界、来源类型和工作目录定下来；这一步决定后续所有上下文怎么传。

寻源动作

主 agent 联网查 SlidingServe，确认 arXiv 2606.05933 是主来源；初步列出 arXiv HTML/abstract、alphaxiv、Sarathi/QoServe 对照来源。后来用户确认“这是论文”，链路转入 PDF 解析。

加载的规则

AGENTS.mdREADME.mdppt-deep-search/SKILL.mdevidence-principleevidence-examplessource-understanding-html-ppt

这些规则约束：产物进 .tmp、HITL 必须等待、Source Understanding 先批准、后续才进入 brief。

工作根

`.tmp/ppt-deep-search/slidingserve-llm-scheduling-capacity/` 成为整个链路的上下文根目录：paper、pdf_xml、review、baselines、final-html-ppt、final-pptx、ccn-report 都从这里展开。

主 agent 输出

不是直接写报告，而是先产出 source-selection、下载 PDF、派发解析子任务，并准备把解析结果作为后续 HTML 和 brief 的证据输入。

Page 4 · PDF 解析子 agent

04 · Source Understanding 与 checker 子 agent

这一阶段的核心不是“生成 HTML”，而是“生成 → 检查 → 用户校准 → 重写”

主 agent 根据 XML 和论文图表做 source_understanding_review.html；多个 checker 子 agent 只看截图和 rubric，不改文件；用户反馈“看不懂”后，主 agent 把语气改成技术小白版。

主 agent 生成

抽取标题、摘要、章节、Figure 1-6、Table 2-5 和关键句；生成 8 页 Source Understanding HTML。

视觉 QA 子 agent

Goodall 首轮 FAIL：第 7 页 Figure 5 太密且底部压线；Parfit/Erdos 后续 PASS。

用户校准

用户指出“技术名词太多，看不懂”，主 agent 重写为技术小白可理解版本。

Rubric checker

Wegener/Raman/Copernicus 按独立 rubric 打分，推动 Figure 5 从小图变为约值表。

Loop 抽象

不展开每次微调，只表达：导出 PNG → checker 反馈 → 修改 HTML → 重新导出。

批准基线

最终写入 baselines/015-source-understanding.md，作为进入 brief HITL 的证据基线。

Page 5 · Source Understanding 生成与 QA loop

05 · 对齐 PPT 大纲和单页 brief

Source Understanding 批准后，主 agent 才进入 PPT brief HITL

这一阶段没有委派子 agent，因为它是用户审批状态机：受众、SCQA、Summary 标题、页数都必须由用户确认后写入 JSON。

受众
用户选择 3：技术管理者 / 架构负责人 / 算力成本决策者

使用场景转为技术评估：判断 SlidingServe 是否可能带来容量、成本或 SLA 改善。

标题
用户指定：SlidingServe 优化vLLM调度，提升30%+

主 agent 不再自拟标题，按用户标题重写 Summary Page。

分析总结
用户指定两条：方法 / 效果

brief 摘要从多点论证压成“方法讲调度机制，效果讲 goodput 和违约率”。

页数
用户指定 1 页

主 agent 生成单页 Summary Page，不再做目录和内容页确认。

产物
ppt_brief_hitl.json + ppt_content_brief.md

脚本生成骨架，主 agent 扩写正文，最终 brief QA passed。

Page 6 · Brief HITL 状态机

06 · 子 agent 制作 HTML，主 agent 审阅修复

HTML 单页由子 agent 生产，但最终质量由主 agent 接管

Huygens 根据 brief 和 html-ppt-skill 做一页 HTML；主 agent 导出截图后发现 Figure 4/5/6 被压缩，进入修复 loop。

Huygens 的生产任务

输入：ppt_content_brief.md、Figure 3/4/5/6、html-ppt-skill。输出：slidingserve-onepage.html，自检页面存在、单页、图片路径正常。

主 agent 的 QA loop

导出 1920×1080 PNG 后，硬校验发现 Figure 4/5/6 缩放低于 80%；主 agent 取消小图堆叠，保留 Figure 4 主图，Figure 5/6 改成指标卡和证据表。

修复后的 HTML

结构变为：顶部标题与 30% callout；左侧方法面板 + Figure 3；右侧效果面板 + Figure 4 + goodput/overload/transient 指标 + 高负载证据表。

验收

validate_source_understanding_html.py 导出通过；主 agent 实际查看截图，确认无破图、重叠、页脚压正文，信息密度适合单页技术管理摘要。

Page 7 · HTML 单页生产与修复

07 · 子 agent 转 PPTX，主 agent 归档

PPTX 阶段的关键要求：可编辑，不是整页截图

Dalton 使用 Codex 原生 presentations skill 和 artifact-tool，把 HTML 内容重建成可编辑 PPTX；主 agent 查 reopened preview、layout JSON 和 QA summary 后归档。

Dalton 的任务

读取 presentations skill 和 artifact-tool docs；输出 1 页可编辑 PPTX。

生成方式

标题、正文、指标卡、证据表、边界卡是 PPT 对象；Figure 3/4 是嵌入图片；不是整页截图。

主 agent QA

查看 reopened preview、layout JSON、qa-summary，确认无明显重叠、裁切、破图或标题换行失控。

归档内容

两个 HTML：source_understanding_review.html、slidingserve-onepage.html；一个 PPTX：slidingserve-onepage-editable.pptx。

路径修复

复制到 paper/ccn-report 后，主 agent 重写 HTML 相对路径，并复制 html-ppt runtime assets 和 pdf_xml_final。

归档验收

对归档内两个 HTML 重新跑导出校验，确认资源路径和图片渲染正常。
