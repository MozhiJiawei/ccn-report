Source Understanding / Incremental BPE

增量 BPE 的核心价值：把“等全文切词”改成“边来边更新”

这篇论文不是换一个 tokenizer API，而是给标准 BPE 找到可证明的增量维护算法：每来一个字节，用最坏 O(log²t) 时间更新最后一个 token，整段输入达到 O(n log²t)，并在部分基准里带来最高约 3x 的端到端吞吐提升。1

O(n log²t)

n 是输入长度，t 是最大 token 长度；这是 BPE 阶段的强 worst-case 保证。

~3x up to

最高增益来自 Hugging Face CodeLlama + Code 数据；不是所有 tokenizer 或所有文本都三倍。

Mental Model

先分清三件事：tokenizer、BPE、增量 BPE

Tokenizer

把人类文本转成模型能读的 token ID。它通常包含清洗、切片、规范化、预分词、BPE 和结果构造。

BPE

从字节或字符开始，按固定 merge rule 把相邻片段合并成更长 token；规则越靠前，优先级越高。

增量 BPE

文本不是一次性给完，而是一字节一字节到来；算法要持续维护每个前缀的标准 BPE 结果。

Raw text你好 world
→
Tokenizer按模型规则加工
→

小白版一句话：tokenizer 是翻译器，BPE 是翻译器里最核心的合并规则，增量 BPE 是让翻译器不用等整句话说完。

Pipeline

BPE 只是 tokenizer 流水线的一段，但它决定最终 token 边界

读图方法

从上往下看：Raw Text 先经过特殊 token splitting、normalization、regex pre-tokenization，最后每个 chunk 才进入 BPE。

这页的边界

论文优化的是 BPE stage，并保持周边 preprocessing 不变；因此“BPE 更快”不自动等于“完整 tokenizer 一定同幅度更快”。

Evidence: Figure 1; Appendix I profiling

Problem

标准 BPE 难流式：后来的字符可能改写前面的最后边界

离线 BPE 的直觉

abcd
abcd
abcd

它会按全局 merge priority 反复合并，直到没有规则可用。

增量 BPE 的难点

abc+ d新字节到来

新字节只加在末尾，但它可能让“最后几个 token”的合并路径变化；算法要避免每次从头重跑。

论文把问题缩小成：追加字符 c 后，只要高效找出新前缀 sc 的最后一个 token θ(sc)，就能维护整段前缀 tokenization。3
Evidence: Problem Formulation; Incremental Objective

Key Insight

结构洞察：可成为最后 token 的候选不是一团乱麻，而是一条单调路径

重构图：蓝色路径表示“可能成为最后 token”的唯一路径；灰色分支被条件排除。

1. 先找最长 suffix token

Aho-Corasick 给出 τ(sc)，它决定搜索哪棵 Suffix-Successor Tree。

2. 再沿单调路径找最深点

论文证明有效候选不会分叉；最深的有效节点就是新前缀的最后 token。

这就是复杂度下降的源头：搜索空间从“所有可能 suffix”变成“一棵小树里找最深有效路径”。
Evidence: Figure 2; Theorem 4.2 Monotonic Path Property

Algorithm

每来一个字节，算法只做三步：定位 suffix、查有效性、找最深节点

1

更新自动机状态

用 Aho-Corasick 维护当前字符串状态，直接得到最长 canonical suffix token τ(sc)。

2

限定搜索空间

只进入 SufSucTree(τ)，不扫完整词表，也不重跑完整 BPE。

3

快速判断候选

用 DFS interval 把 Prefix Last-Token Condition 变成 O(1) 区间检查。

4

沿 centroid 搜索

用 Centroid Decomposition 在树里找单调有效路径的最深节点。

append(byte) → AC state → τ(sc) → SufSucTree(τ) → deepest valid θ(sc)
Evidence: Section 5 Algorithm Framework

Streaming Output

增量维护还不够，eager output 解决“什么时候能吐 token”

输入流式

文本字节到来时，算法能更新当前前缀 tokenization。

输出稳定

只有当某个 token 边界未来不再被改写，才可以安全发给下游模型。

额外代价

论文报告 eager output 需要维护动态子图，端到端吞吐约有 10% 量级 overhead。6

Benchmark

“最高 3x”成立，但它是分场景的最高值，不是平均承诺

读法该怎么讲
强信号当 BPE 本身是主要瓶颈时，增量算法可以带来显著 end-to-end speedup。
别外推Qwen-3、DeepSeek、GPT-OSS、Llama 等许多行只在 1.0x 附近。
真实口径实验是 drop-in 替换核心 BPE，周边 normalization / regex / caching 保持原配置。
给后续 PPT 的标题口径：增量 BPE “最高约 3x”，而不是“所有推理吞吐提升 3 倍”。
Evidence: Table 1; throughput analysis

Robustness

更硬的价值在鲁棒性：重复字符输入会让部分 baseline 接近平方退化

为什么这重要

生产 tokenizer 不只要平均快，也要防止某些输入触发极慢路径，形成延迟尖刺或 DoS 风险。

论文证明什么

增量 BPE 用 worst-case bound 控住 BPE 阶段成本；重复字符不再让核心 BPE 随输入长度平方级恶化。

Evidence: Figure 3; Figure 7; Impact Statement

Decision Frame

后续 PPT 应把它讲成“值得复现的 tokenizer 内核改造”，而非直接上线结论

已经有证据支撑

  • 标准 BPE 可被精确增量维护。
  • BPE 阶段有 O(n log²t) worst-case 保证。
  • 部分 HF tokenizer 场景有最高约 3x end-to-end speedup。
  • 病理输入下稳定性明显优于 baseline。

还不能直接外推

  • 完整 tokenizer pipeline 可能被 regex 或 normalization 主导。
  • eager output 有额外维护成本。
  • “推理吞吐 3 倍”需要结合本地 I/O、prefill、batching 和模型服务栈复测。
  • 工程接入要评估 Rust 内核、词表兼容、缓存和回滚路径。
一句话基线：它让 BPE 从离线批处理步骤变成有 worst-case 保证的流式内核；真正的推理吞吐提升，需要看 tokenizer 是否是本地 pipeline 的关键路径。
Evidence: Abstract, Table 1, Table 6, Appendix I, Future Work
