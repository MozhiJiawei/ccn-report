Source Understanding Deck · HITL Approval

Agent 的高风险操作，为什么要先“停一下”？

面向技术小白的心智模型：HITL 不是给 Agent 加一个弹窗，而是在工具执行前插入可审计、可恢复、可拒绝的人工决策点。

白底工程化 机制图 三方来源对照 脚注可追溯
问题背景
资损、不可逆变更、合规审计让 Agent 不能直接执行所有工具。
关键机制
工具调用被标记、执行前中断、人工决策、从持久化状态恢复。
效果边界
HITL 控制工具层副作用，不替代权限、审计、规则覆盖和状态版本治理。

结论先行

1
HITL 的本质是“工具调用闸门”。
模型可以提出动作，但执行权被运行时/安全层拦截，直到人给出决策。
2
落地质量取决于三件事。
触发策略是否准、暂停状态是否可恢复、审批决策是否不可伪造且有审计。

01 · Mental model

把 Agent 想成“会申请操作的实习生”，HITL 是主管签字台

模型推理

决定下一步要调用哪个工具

工具申请

例如删除数据、执行 SQL、发邮件

HITL 闸门

检查风险策略，必要时暂停

执行 / 不执行

取决于人工决策与恢复状态

Approve

按原参数执行工具

Edit / Reject

改参数或拒绝执行

Respond

人作为 ask_user 类工具的回答源

读图方法

  • 先看中间闸门：HITL 发生在工具真正执行之前。
  • 再看下面决策：不同框架支持的人工回复语义不同，不应混用。
  • 最后看恢复：暂停不是崩溃，必须保存运行状态，之后从同一上下文继续。
边界：HITL 只能控制“被工具层捕获的动作”。如果危险行为绕过工具系统或审批策略没有覆盖，它不会自动变安全。
mental model
LangChain 描述 middleware 在工具调用需要 review 时发出 interrupt 并依赖 persistence 保存图状态 [S2]；OpenAI Agents SDK 描述工具声明 approval，RunState 序列化并恢复 [S3]。
这里用一个生活化比喻建立模型：Agent 不是直接操作生产系统，而是先提交操作申请。HITL 闸门既看风险，也负责把暂停和恢复做成工程机制。

02 · Problem background

问题不是“模型会不会犯错”，而是“模型的动作会不会造成不可逆后果”

三类风险推动 HITL

风险类型小白解释典型动作
资损 / 数据损坏一旦执行，损失难以回滚批量删除、退款、取消订单
权限 / 合规系统需要留下谁批准了什么生产变更、敏感数据访问
中间地带不该硬拦，也不能直接放行写文件、执行非 SELECT SQL

二态安全不够用

只 PASS / BLOCK

低风险自动放行，高风险硬拦截；但合理的高影响动作会被卡死。

加入 HITL

把“合理但需确认”的动作转成暂停、通知、人工决策、恢复。

结论：HITL 是为“高影响但不一定错误”的操作提供第三条路。
risk background
掘金来源明确指出资产和金额相关操作直接开放给 Agent 容易造成资损，并将 HITL 定义为“暂停 → 通知 → 等待人工决策 → 恢复/终止” [S1]。
这页解释为什么不是所有东西都自动化。对小白来说，关键是理解 HITL 不是怀疑模型，而是对不可逆副作用做治理。

03 · Common mechanism

三套资料共同指向同一个四段式机制：标记 → 中断 → 决策 → 恢复

1. 标记风险动作

needs_approval / interrupt_on / OperationGuard 规则

2. 执行前中断

工具调用被拦截，返回 pending approval

3. 人给出决策

approve / edit / reject / respond 或批准/拒绝

4. 从状态恢复

RunState / checkpoint / worker 恢复上下文

S1 Harness
OperationGuard 把 HITL 作为 PASS/WARN/HITL/BLOCK 之一；流程包含 Token、WS/IM、超时和审计。
→
S2 LangChain
middleware 检查工具调用策略，触发 interrupt；Graph state 由 checkpointer 保存，resume 时提交 decisions。
→
S3 OpenAI Agents
工具通过 needs_approval 标记；RunResult.interruptions 暴露待审批项；RunState approve/reject 后继续。
unified mechanism
机制归纳来自三方资料共同模式：S1 的 Harness 安全层、S2 的 middleware/interrupt/checkpointer、S3 的 needs_approval/interruption/RunState。
这页是全 deck 的核心。要告诉听众：虽然各家名词不同，但四段式是一样的。读图时从左到右看，任何少一段都会出问题。

06 · Lifecycle

一次审批从“喊停”到“恢复”，至少有 5 个状态

STATE 01

拦截

Agent 产生工具调用；安全层或 middleware 判定需要审批。

STATE 02

挂起

生成 interrupt / pending approval；工具还没有真正执行。

STATE 03

持久化

保存 graph state / RunState / Agent 工作现场，等待稍后恢复。

STATE 04

决策

人在线弹窗、IM 卡片、控制台或业务审批页给出决定。

STATE 05

恢复

批准则执行；拒绝则返回反馈；超时通常自动拒绝。

小白关键点：暂停的是“运行状态”，不是“聊天记忆”。没有可恢复状态，审批回来后 Agent 可能不知道自己停在哪里。
边界：S1 描述在线、离线、30 分钟超时与数据库兜底扫描；S2/S3 主要给出框架级中断和恢复 API，并不内置同一套企业通知/超时策略。
approval lifecycle
S1 完整生命周期包括在线批准/拒绝、离线 IM 审批、30 分钟超时自动拒绝；S2 要求 checkpointer 和同一 thread ID；S3 使用 RunState 序列化并恢复。
强调“暂停不是失败”。这个概念对初学者很关键：运行时要能把当前堆栈/图状态/上下文保存下来，之后同一条任务继续。

07 · Decision semantics

“同意/拒绝”不够精细：不同决策会改变 Agent 看到的世界

决策工具是否执行Agent 收到什么容易踩坑
approve是，按原参数执行真实工具结果审批人要确认参数没有被提示注入或误判
edit是，但使用人工修改后的参数修改后工具结果大幅修改可能导致模型重新规划甚至重复调用
reject否拒绝反馈 / 合成 ToolMessage应明确是否禁止重试、改走安全方案或追问
respond否，人就是工具结果人类回复被当作成功结果不能用它拒绝有副作用工具，否则模型会以为执行成功
判断：面向业务高风险动作时，默认只给 approve/reject；把 edit/respond 开给谁、开到什么工具上，需要额外治理。
decision semantics
四种决策语义来自 S2；S2 明确提醒 respond 只适合 ask_user 风格工具，不应用于拒绝 side-effecting tools；S3 主要聚焦 approve/reject 并支持自定义 rejection message。
这页讲“看似只是按钮，其实会改变执行语义”。尤其提醒 respond 的坑：它会被当成成功工具结果。

长等待：S3 建议为 pending approvals 存版本标记，避免模型、提示词或工具定义更新后无法反序列化或语义漂移。

edge cases
S1 描述多工具聚合与一次 Token；S2 描述 multiple decisions 必须按 interrupt action 顺序提供；S3 描述 nested Agent.as_tool 审批、RunState 持久化和 pending task versioning。
