Why

单 agent 最简单，但当能力数量、上下文和团队边界膨胀时，系统需要更清晰的协调方式来避免 prompt 混乱。

What

文章给出四种基础架构模式：subagents、skills、handoffs、routers，并用控制权、状态、上下文隔离和延迟成本来区分。

How

从最关键约束反推选择：需要集中控制选 subagents，需要轻量专业化选 skills，需要用户直达专家选 handoffs，需要确定分类选 routers。

多 agent 不是默认答案

文章先强调应从单 agent 和好工具开始，只有 context management 与 distributed development 成为瓶颈时再引入多 agent。

四种模式解决的是不同协调问题

subagents 强调主管编排，skills 强调按需加载知识，handoffs 强调转交控制权，routers 强调确定路由。

选择标准来自约束而不是偏好

延迟、token、团队所有权、状态保持、用户体验和安全边界共同决定架构。

这篇文章的论证链路

观察记录真实输入、输出、工具调用和上下文。
归纳把单次行为聚合成模式、失败类型或业务信号。
评价用 traces、datasets 或在线评分验证改动。
改进调整 prompt、工具、模型、memory 或 runtime。
