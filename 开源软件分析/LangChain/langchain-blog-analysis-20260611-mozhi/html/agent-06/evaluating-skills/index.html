Evaluating Skills

Why：技能会改变编码 agent 的行为，凭感觉判断很容易漏掉退化。What：LangChain 把技能评估做成一组可对照的实验：无技能、全技能、合并技能、拆分技能。How：在干净沙箱中运行固定用例，用完成率、调用率、轮次和耗时衡量结果，再用 LangSmith 追踪每一步失败原因。

Why技能本质上是按需加载的提示与资源，需要像提示一样被测试。
What原文给出一条从用例设计到实验比较的评估管线。
How固定环境、可判分用例、模块化技能、LangSmith 观测形成闭环。
作者：The LangChain Team / Robert Xu 日期：March 5, 2026 阅读时间：10 min 类型：技术长文

技能评估的核心不是评分一次，而是比较变化。

原文的基本管线很克制：先定义希望 Claude Code 完成的固定用例，再定义会帮助这些用例的技能；分别运行“无技能”和“有技能”的版本，最后比较表现并迭代技能内容。

1. 定义用例从真实失败中抽取最小可复现场景。
2. 定义技能把说明、脚本和资源组织成 agent 可加载的材料。
3. 无技能运行建立对照组，知道 baseline 能到哪里。
4. 有技能运行替换不同技能组合，观察增益和副作用。
5. 比较迭代用结果和轨迹反推技能内容哪里有效。

环境越干净，评估越像在测技能本身。

编码 agent 的动作空间很大，而且会被起始目录里的文件影响。LangChain 在测试中使用轻量 Docker scaffold 运行 Claude Code，也提到 Harbor 或其他 sandbox 可作为替代；重点是让每次起点一致，让结果可复现。

这篇文章反复强调一个边界：评估技能时，实际上也在评估 agent 是否能有效使用这份技能材料。

好用例要可判分，而不是只看输出像不像。

文章建议减少开放式生成，优先让 agent 修复带 bug 的代码，或完成有明确产物的用例。这样可以通过预定义检查判断是否正确，而不是让评估停留在主观感受。

技能是否被调用

相关时被调用，不相关时不被调用，能衡量触发描述是否清楚。

是否完成步骤

把总失败和接近成功区分开，帮助定位短板。

轮次与真实耗时

即使完成率相同，技能也可能通过更少轮次提升效率。

技能内容要按可替换单元迭代，而不是逐字打磨。

LangChain 的经验是，300 到 500 行的大技能中，细微措辞或格式变化影响有限；更有价值的是把内容拆成带 XML 标记的段落，便于整体替换或移除，做 A/B 对照。

文章还指出 AGENTS.md 和 CLAUDE.md 的价值：技能不一定总被 agent 调用，而这些文件会稳定进入上下文，适合放“何时调用技能”和“多个技能如何配合”的指引。测试中，在约 20 个相似 LangGraph 技能时 Claude Code 有时会选错；减少到 12 个时调用更稳定。

LangSmith 把失败从黑盒变成可追踪轨迹。

原文给出的强信号是：Claude Code 搭配技能的完成率达到 82%，没有技能时降到 9%。但文章没有停在这个数字，而是强调还要理解为什么失败。LangSmith 记录 agent 读了哪些文件、写了哪些脚本、调用或漏调了哪些技能。

实验页让技能拆分、合并和对照组同屏比较。

文章列出的实验条件包括无技能对照、全技能、少数大技能、多个小技能。不同拆法会在不同用例上表现更好，所以评估平台需要同时看完成率、检查通过率、耗时和轮次，而不是只看单一分数。

最后的落点：技能和其他 agent 组件一样，需要工程化评估。

文章把 skills 定义为面向特定领域的说明、脚本和资源，并通过 progressive disclosure 按需加载。它们能增强 Claude Code、Codex 或 Deep Agents CLI，但也可能以意外方式改变行为。可复现环境、清晰用例、模块化内容和可观测实验，是把“感觉更好”变成“确实更好”的路径。
