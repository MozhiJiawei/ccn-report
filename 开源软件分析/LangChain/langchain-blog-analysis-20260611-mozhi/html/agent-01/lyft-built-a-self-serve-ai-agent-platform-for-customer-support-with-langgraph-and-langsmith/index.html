Why

Lyft 客服场景扩张后，靠 MLE 把领域专家需求翻译成 agent 配置的模式太慢。

What

他们用 LangGraph 构建自助式多 agent 平台，并用 LangSmith 跟踪、评估和监控生产质量； configurable agent 开发从约 6 个月降到约 2 周。

How

meta agent 路由 rider/driver 请求到专门 subgraph，配置型 agent 由 JSON 和 Prompt Hub 动态生成，DynamoDB checkpoint、生产 traces、LLM-as-a-judge 和 dashboard 共同守住质量。

路由型多 agent 架构让复杂客服流可拆。

meta agent 先分类请求，再把控制权交给 rider、driver 或更专门的 damage claim 等 subagent。若对话中意图变化，subagent 可把控制权交回 parent graph 重新路由。

自助层和高风险层分开治理。

复杂高风险流程仍由 MLE 手工构建 specialized agents；常规问题则成为 configurable agents，由领域专家写结构化 prompt 和 JSON config，平台负责 graph、tool、safety 和 state。

LangSmith 把迭代从主观评审变成生产信号。

所有环境的运行都 tracing 到 LangSmith；上线前从 5-10% 低流量生产 traces 采样，运行多轮 judge evaluators，并用 dashboard 监控 volume、error、latency、token、tool success 和分数趋势。

最大的瓶颈变成 prompt 质量。

Lyft 发现基础设施不是最难点，领域 prompt 的 scope、branching 和 exit conditions 才是稳定性关键，因此建立五部分 prompt 模板和 Git-backed prompt linting。
