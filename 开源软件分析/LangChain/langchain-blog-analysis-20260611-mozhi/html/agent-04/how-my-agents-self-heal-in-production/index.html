How My Agents Self-Heal in Production

Why：部署后的回归问题通常需要人工看日志、判断是否由本次改动引入、再写修复；这正是 coding agent 可以闭环处理的生产运维工作。 What：作者为 GTM Agent 搭了 self-healing deployment pipeline：每次部署后自动捕获 build/server 日志，检测回归，triage 因果，再让 Open SWE 开修复 PR。 How：流程分两路处理 Docker build failure 与 post-deploy server errors；服务器错误用 Poisson test 判断本次部署后是否显著上升，再由 triage agent 和 Open SWE 连接诊断与修复。

Why

部署后的回归问题通常需要人工看日志、判断是否由本次改动引入、再写修复；这正是 coding agent 可以闭环处理的生产运维工作。

What

作者为 GTM Agent 搭了 self-healing deployment pipeline：每次部署后自动捕获 build/server 日志，检测回归，triage 因果，再让 Open SWE 开修复 PR。

How

流程分两路处理 Docker build failure 与 post-deploy server errors；服务器错误用 Poisson test 判断本次部署后是否显著上升，再由 triage agent 和 Open SWE 连接诊断与修复。

一句话带走

这篇文章把“agent 自我修复”落到一条生产管线：部署后先抓日志，再判断错误是否因本次变更显著上升，随后由 triage agent 定位原因，最后交给 Open SWE 写 PR。核心不是自动合并，而是把人工排障前的重复环节自动化。

文章真正强调的三件事

先区分构建失败和线上回归

Docker build failure 可以直接用日志和 diff 触发修复；server-side regression 需要先和背景错误率区分。

Poisson test 给回归一个统计门槛

文章用部署前后错误签名的发生率变化判断是否异常，避免 transient failure 触发噪音。

Open SWE 负责把诊断变成 PR

triage agent 判断改动相关性和根因，Open SWE 基于 issue 内容研究代码、写修复并打开 PR。

支撑观点的机制

自愈流程从部署事件开始

GTM Agent 部署到生产后，GitHub Action 捕获 build logs 和 server logs。构建失败走即时修复路径，运行时错误走统计检测与 triage 路径。

统计门槛防止把背景噪音当事故

生产系统本来就会有网络、第三方 API 和瞬时失败。文章用 Poisson test 比较部署窗口前后的错误率，只把显著上升的签名送入 triage。

闭环的边界停在代码审查前

自动化负责发现、归因和生成修复 PR；人工仍在 review time 介入。这让 pipeline 更像 fix-forward 的前置加速器，而不是无人值守发布系统。
