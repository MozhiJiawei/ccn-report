技术长文 · February 10, 2026 · 6 min

Why越来越多 agent 需要一台隔离的 computer 来运行代码、安装包和访问文件，关键问题从是否 sandbox 变成如何连接 sandbox。
What文章区分两种架构：Agent IN Sandbox 和 Sandbox as Tool，前者贴近本地开发但密钥和通信复杂，后者隔离 agent state 与执行环境但会引入网络延迟。
Howdeepagents 可通过配置支持两种模式；选择依据是环境耦合度、迭代速度、API key 边界、state 分离和 provider 通信能力。

Agent IN Sandbox 适合环境强耦合

agent 和执行环境一起跑在 Docker 或 VM 中，外部通过 HTTP/WebSocket 发送消息。好处是像本地开发，agent 能直接访问文件系统和环境状态；代价是需要跨边界通信层，API keys 进入 sandbox，更新也要 rebuild image。

Sandbox as Tool 适合快速迭代和密钥隔离

agent 在本地或服务器上运行，需要执行代码时调用 E2B、Modal、Daytona、Runloop 等 provider API。agent state、conversation history、memory 留在 agent runtime，sandbox 失败不丢 state，也更容易更换 backend。

安全和权限边界是文章的核心比较维度

Pattern 1 中 bash tool 与 agent 共享较大权限面，code 和 prompts 也更容易被 exfiltrate；Pattern 2 把安全边界围绕执行工具本身，API keys 留在 sandbox 外。

选择标准不是绝对优劣，而是耦合与运行成本

文章建议：环境和 agent 紧耦合、希望生产贴近本地、provider 处理通信层时选 Pattern 1；需要快速更新 agent logic、API keys 不进入 sandbox、agent state 与执行环境分离时选 Pattern 2。
