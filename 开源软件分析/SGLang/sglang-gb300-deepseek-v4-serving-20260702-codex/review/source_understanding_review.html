Mental model

LLM 推理服务像一条两段流水线：先“读题”，再“逐字输出”

DeepSeek-V4 难服务，是因为长输入、MoE 专家路由、KV cache、speculative decoding 和多 GPU 并行同时存在；速度取决于 GPU 是否能在 prefill 与 decode 之间持续吃满工作。

1. Prefill / 读题

把用户输入的 8K token 一次性处理，建立注意力状态与 KV cache。这里容易被 MHC、compression、CUDA graph break 等开销拖慢。[2]

→

2. Decode / 逐字输出

每轮生成下一个 token，持续消耗 KV cache 与 attention/MoE 计算。这里的关键是 batch 能做多大、SWA 内存预算是否准确。[3]

→

3. User interactivity

用户感知为 tok/s/user。文章用相同 interactivity 比较吞吐，避免只追求总 tok/s 却让单个用户变慢。[1]

吞吐量 tok/s/GPU 是什么？

每块 GPU 每秒服务多少输出 token。越高通常代表同样硬件能服务更多用户，成本更低。

tok/s/user 是什么？

单个用户看到答案吐字的速度。文章强调“same interactivity”，说明比较时没有靠牺牲用户体验换吞吐。

术语小白理解在本文里为什么重要相关优化
MoE不是每次都跑所有专家，而是路由到部分专家。DeepSeek-V4 serving 难点之一，FP4 MegaMoE 路径影响高吞吐区。W4A4 MegaMoE
KV cache模型记住前文的“状态缓存”。长上下文和高并发时显存预算会限制 batch。KV Compression V2 / SWA budgeting
CUDA graph把常见 GPU 执行流程提前录好，少走 CPU 调度。prefill path 不规则时容易退回 eager islands。breakable CUDA graph

Mechanism 1 / Kernel path

内核优化的核心：少搬中间结果、少拆小步骤、让 FP4/MoE 与压缩路径更贴模型

Kernel lane
瓶颈位置
改造动作
曲线如何移动
MHC / Prefill
mhc_pre、RMSNorm、hc_head、post-pre 分散，产生中间 tensor traffic、kernel launch 和 scheduler boundary。
→ fuse#24775 deeper fused MHC；RMSNorm 融入 MHC；dedicated fused hc_head；#25976 fused mhc_fused_post_pre。[1]
prefill 热路径边界减少，读长输入时的非 matmul overhead 降低；同样 interactivity 下更容易承载更高请求压力。
KV Compression
长上下文和高并发下，compression / indexer / rope 不是旁路小事，会跟 matmul 一起决定吞吐。
→ specialize#24890 V2 c4、c128、online c128 compression kernels；fused norm/rope V2。[2]
KV 状态压缩路径跟得上并发增长，避免 GPU 在压缩/索引小内核上被拖住。
FP4 MoE
expert weights 已是 MXFP4，但 activation path 仍走 MXFP8，MoE 高吞吐区效率未完全贴合 FP4 recipe。
→ quantize#25052 W4A4 MegaMoE：activation path 也转 MXFP4，来源称 negligible accuracy loss。[3]
MoE 专家路径在 higher-throughput operating range 更高效；MTP / no-MTP 两条 serving frontier 都能受益于更强底座。

Mechanism 2 / Runtime path

运行时优化的核心：预算更准、batch 更大、图捕获更多、配方更贴场景

effective throughput ≈ usable batch × GPU utilization ÷ runtime overhead

1. Budget

变量：usable batch。

full-length accounting 与 SWA tail resident pool 分开；waiting / running / transfer 状态按更真实 token reservation 处理。

#24036 + #24857 → fewer false memory limits

2. Admission

变量：batch stability。

decode worker 不会因为过度预留显存过早拒绝请求；高并发时 effective batch 可以维持更久。

larger batch → GPU less idle

3. CUDA graph

变量：runtime overhead。

breakable CUDA graph 让更多 DeepSeek-V4 prefill path 回到 graph-friendly execution，减少 host-bound 调度。

#25195 + #25795 → lower overhead

4. Recipe dispatch

变量：GPU utilization。

按并发和部署场景调 prefill/decode ratio、parallel plan、KV allocation、token/request limits 和 tokenizer。

scenario recipe → better utilization

Outcome

读图：左到右是 control loop，不是独立清单。

预算决定可进入多少请求；准入维持 batch；graph 降低 runtime tax；recipe 让 GPU 在该并发点更忙。

curve holds deeper into high interactivity

Mechanism 3 / Hardening

稳定性修复也是性能：一旦 metadata、显存、数值或负载分布出错，性能曲线会塌

Speculative + disaggregated bugs

#23919 修 PD-MTP metadata buffer hidden-size bug；#25805 修 disaggregated decode + MTP speculation 下 SWA memory double-free。[1]

意义：speculative path 不是“能跑一次”就够，必须能撑过真实并发 sweep。

Compile behavior

#25810 增加 representative MHC token-count bucket prewarm，避免首批真实请求持续支付 lazy compile 成本。[2]

意义：系统应提前知道 hot shapes，不在关键路径重新发现。

Numerics + imbalance

#25733 修 Blackwell 上 DeepSeek-V4-Pro NaN；文章称一次 observed run 中 acceptance rate 从 0.57 到 0.70。Dynamo #9080 减少 DP rank workload imbalance。[3]

意义：看似 correctness 的修复，会改变 MTP 接受长度和 live frontier。

“Bug-fix bucket is part of the performance story, not separate from it.” [4]

Mitigation chain

acceptance 0.57 → 0.70 的口径

来源只说这是 #25733 修复 Blackwell FP8-einsum scaling 后的 one observed run；它支持“数值修复会恢复 MTP path”的方向判断，不是通用验收率基准。

读图：0.57 和 0.70 是同一修复线索下的 observed acceptance rate，不要外推成稳定 SLO。

为什么会影响吞吐曲线

MTP/speculative decoding 的价值来自“猜中更多 token”。接受长度或接受率下降时，MTP 曲线的高吞吐 frontier 会被压低。

所以 correctness fix 会通过 speculative path 间接影响吞吐。

为什么是 hardening 而不是杂项

metadata sizing、double-free、lazy compile、NaN、DP rank imbalance 都会让系统避开好 recipe 或在并发 sweep 中塌掉。

结论：hardening 是把更快路径变成可信路径。

Can say / 能说

  • 在 PyTorch 文章描述的 InferenceX GB300 disaggregated lane 条件下，June MTP 曲线相对 Day-0 no-MTP 给出 5x headline。

Takeaway model

最后带走这个模型：性能提升 = 更少无效工序 + 更准运行时调度 + 更少稳定性陷阱

Kernel：把 GPU 工序做紧

MHC fusion、KV Compression V2、W4A4 MegaMoE 减少边界和非 matmul 开销，让 prefill/compression/MoE 更贴 DeepSeek-V4。[1]

+

Runtime：把请求排得更准

SWA budgeting、decode admission、CUDA graph、tuned recipes 让 batch 和显存更贴真实并发，GPU 更少空转。[2]

+

Hardening：让好路径站得住

metadata、double-free、NaN、compile prewarm、DP imbalance 等修复，让 MTP/disaggregated path 在并发 sweep 中更可信。[3]

一句话版：SGLang 的 5x 故事不是“某个模块突然快了”，而是把 DeepSeek-V4 在 GB300 上服务时的关键堵点逐个清掉：GPU 算得更连续，显存和 batch 管得更准确，speculative/disaggregated 路径更稳定。

可复述模板

  • 指标：在约 50 tok/s/user 交互速度下，June MTP 曲线约 11,200 tok/s/GPU，对比 Day-0 no-MTP 约 2,200。
  • 问题：DeepSeek-V4 serving 难在 prefill、decode、KV cache、MoE、speculative path 和多 GPU 并行同时约束吞吐。
  • 动作：kernel fusion / KV Compression V2 / W4A4 MegaMoE / SWA budgeting / CUDA graph / recipes / hardening。
  • 边界：GB300 disaggregated lane，DeepSeek-V4 Pro，FP4，8K/1K，dynamo-sglang。

不要这样复述

  • 不要说“DeepSeek-V4 模型本身快了 5 倍”。来源讲的是 serving stack 曲线。
  • 不要说“某个 kernel 单独带来 5 倍”。来源不是逐项 ablation。
  • 不要把 5x 推广到所有硬件、所有上下文长度、所有推理框架。
  • 不要忽略 hardening：metadata、NaN、double-free、compile prewarm、DP imbalance 都是性能故事的一部分。
